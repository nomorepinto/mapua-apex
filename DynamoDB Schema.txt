Reorganized schema

ORGANIZATION
PK: ORGANIZATION#uuid
SK: ORGANIZATION#uuid
name: string
is_higher_council: boolean (default false)
signatories: [
  { role: "adviser", signatory_id: "adv001" },
  { role: "dean",     signatory_id: "dean001" }
]
Desk directory for this org (one person per role).
Allowed desk roles: adviser | dean | osaar | cdm | admin.
Stored in that role order even if the write sent a different order.
Not stored on SIGNATORY. Approval routing uses org desks for adviser
and dean. If is_higher_council is true, Dean is skipped; Adviser still
reviews first.
OSAAR and CDM are campus-wide: OSAAR_SIGNATORY_ID and
CDM_SIGNATORY_ID in the API env (plain uuid or SIGNATORY#uuid).
Rename those people in place (PUT /signatories on the same id).
admin may occupy a desk but is not in the approval sequence.
GET /public/organizations scans these base items without authentication and
returns only the bare organization_id and name for the account signup picker.
DELETE /admins/organizations/{id} is guarded: it removes the ORGANIZATION item
only when the org owns no EVENT/SUBMISSION rows (GSI1PK = ORGANIZATION#id) and
no COLLABORATION POINTER rows (PK = ORGANIZATION#id, SK begins COLLAB#);
otherwise it returns 409 and leaves the item untouched. Delete does not rewrite
student Cognito custom:organization_id.

ORGANIZATION MEMBER (apex-owned roster)
PK: ORGANIZATION#uuid
SK: MEMBER#studentId
lastname: string
firstname: string
student_number: string

The organization's member roster, owned and managed by mapua-apex through
/api/v1/students/members (GET list, POST one, POST bulk CSV import, PUT edit
name, DELETE remove). A create is guarded by attribute_not_exists(SK), so a
student number is unique within the org (409 on duplicate); bulk import writes
in 25-item BatchWriteItem chunks and reports duplicates as skipped rather than
failing the batch. This is the authoritative membership list — arcus-attendance's
"Allow members only" scanner toggle reads these rows (GetItem
PK=ORGANIZATION#{org}, SK=MEMBER#{studentId}) to decide whether a scanned
student may check in to that org's event. It is distinct from the arcus STUDENT
profile (arcus-owned identity, see ATTENDANCE CHECK-IN below) and replaces the
deprecated arcus-written ORGANIZATION + MEMBER join rows noted there.

EVENT
PK: EVENT#uuid
SK: EVENT#uuid
sent_at: timestamp
GSI1PK: ORGANIZATION#uuid
GSI1SK: timestamp

The deadlines list walks GSI1 EVENT items (first 25, oldest first), then
each event’s DEADLINE# children. The org submission list no longer walks
events: it reads SUBMISSION rows straight off GSI1 (GSI1SK begins
SUBMISSION#), same as admin, so every paper is returned regardless of
event count. Student GET /organization reads this ORGANIZATION item
directly.

Deny sets status
"denied", drops GSI2, and the student cannot edit. GSI2 is also dropped
on the last approve (status stays "approved" / "denied", current_signatory
is left as the last desk).
"finished" is a terminal, post-approval status set only when OSAAR approves the
event's post-evaluation (see POSTEVAL: a post-eval going submitted -> approved
also transitions the linked SUBMISSION approved -> finished); like "approved"
and "denied" it is not editable. There is no "ongoing" status — an event
starting is recorded in the activity log only (deferred until logging ships).
On the last approve the backend also writes an "event scheduled" NOTIFICATION
(system-created, not client-postable) that surfaces in the org_submitter
Timeline Reminders and triggers an SES email with the arcus attendance and
evaluation links.
The arcus apps reach the backend over three server-to-server GET endpoints
(shared secret ARCUS_SERVICE_TOKEN, not a Cognito JWT):
- /api/v1/arcus/events: approved/finished submissions in the requested window.
  Attendance uses window=attendance (event day); evaluation uses window=evaluation
  (event day through ARCUS_POST_EVALUATION_WINDOW_DAYS, default 3, Asia/Manila).
  X-Arcus-Organization-Id scopes the list; omitted means cross-organization.
- /api/v1/arcus/students/{studentId}/events?window=evaluation: published in-window
  events filtered by BatchGetItem of EVENT#{eventId}/MEMBER#{studentId}. Keys are
  deduplicated and chunked at 100, with strongly consistent reads and up to five
  attempts for unprocessed keys; exhaustion fails rather than omitting attendance.
  No reverse GSI is required. Arcus asserts studentId from the verified claim.
  As with /events, omitting window selects attendance.
- /api/v1/arcus/events/{eventId}/post-eval: SUBMISSION# and POSTEVAL# prefix reads,
  then live attendance/evaluation aggregation after the organization scope check.
  Prefer an active POSTEVAL, otherwise the latest denied filing by submitted_at,
  and resolve its linked submission. Orphans are ignored. With no filing, prefer
  the newest approved/finished submission and return post_eval.status=none with
  null ID/timestamps. Unknown event returns 404; wrong organization returns 403.
  Arcus additionally enforces officer role and event window before forwarding.
The former POST /api/v1/arcus/events/{event}/submissions/{submission}/finish route
is RETIRED — only OSAAR post-evaluation approval sets a submission to finished.

SUBMISSION
PK: EVENT#uuid
SK: SUBMISSION#uuid
submission_type: string
sent_at: timestamp
status: "pending" | "approved" | "denied" | "returned" | "finished" | "cancelled"
  ("cancelled" is RESERVED for the deferred EventBridge auto-cancel — when an
  event's 3-day post-evaluation window lapses with no filed post-eval the linked
  submission becomes "cancelled" (+ cancelled_at). No code path writes it yet;
  see mapua-apex/todo.md item 2.)
current_signatory: SIGNATORY#uuid
signatory_sequence: [ SIGNATORY#uuid ]   (ordered routing snapshot, written at submit time; the ONLY stored form of the chain — signatory_chain is derived at read time, never persisted)
collaboration: {
  dependent_organization_ids: [ ORGANIZATION#uuid ]   (index-only collaboration dependents; empty/absent = no collaboration)
}
GSI1PK: ORGANIZATION#uuid
GSI1SK: SUBMISSION#uuid
GSI2PK: SIGNATORY#uuid   (sparse: present while pending or returned on a desk)
GSI2SK: timestamp
finished_at: timestamp   (sparse: stamped when status becomes "finished" via OSAAR post-evaluation approval — see POSTEVAL)

activity_classification: {
  activity_type: "co-curricular" | "extra-curricular"
  total_org_members: number
  nature: "major" | "minor"   (OSAAR-set via the signatory classification PATCH; not part of the student create body)
}
proponents: [{
  id, position_title, first_name, middle_name, last_name, suffix,
  student_number, program_and_year, date_of_submission, department,
  position_of_applicant, org_or_course_section, contact_number,
  email_address, facebook_link
}]
activity_details: {
  title_and_nature, description, objectives, venue,
  date_of_event, day_of_event, time_of_event,
  expected_participants, individual_contribution, proposed_budget
}
time_of_event is 24-hour "HH:MM - HH:MM" (start and end).
The form lists hours 1–12 and minutes in 5-minute steps. Saved times must fall between 7:00 AM and 9:00 PM. End is not earlier than start, and start and end cannot be the same.
institutional_alignment: {
  mission_statements: { competitive, research, solutions }
  core_values_explanation, peo_explanation, sdg_explanation
}
detailed_budget_proposal: {
  items: [{ item_no, unit, quantity, price_per_unit, total }]
  grand_total
}
venue_reservation: {
  has_reservation: boolean
  reservations: [{
    reservable_id: RESERVABLE#uuid (or bare uuid)
    campus_id: CAMPUS#uuid (or bare uuid)
    name: string                 (snapshot of the reservable name at submit time)
    type: "room" | "equipment"
    selections: [{ date: "YYYY-MM-DD", slots: [int 0-11] }]
    remarks: string
  }]
}
booking_refs: [{ pk: "RESERVABLE#uuid", sk: "BOOKING#uuid" }]
  (sparse: present only while the paper holds bookings; removed on deny/return)
has_reservation true routes the paper through the CDM desk. Each reservations[]
entry is one picked RESERVABLE (a room or equipment item under a campus) with
its concrete selections. On submit the API validates every { date, slots }
against the reservable's weekly template and the existing approved BOOKINGs,
then writes source:"submission" BOOKING holds with approval_status "pending"
and stores their keys on booking_refs (see BOOKING). A slot taken in the
meantime aborts the write with 409 and persists nothing. Pending holds do not
occupy slots; the CDM desk's approval (the last step) re-checks them and flips
them to "approved" (409 with nothing written if a slot was taken). Deny and Return release booking_refs and remove the attribute; a
student re-edit reconciles them (releases removed, plans added). slots are
0-based indices into the canonical 07:00-21:00 day split into 70-minute slots
(exactly 12; slot i starts 07:00 + i*70min, slot 11 = 19:50-21:00); Sunday is
never reservable. activity_details.venue is stored as sent: when a paper
includes a reservation the venue is the chosen CAMPUS name (the campus list now
comes from the CAMPUS objects, no longer a hardcoded pair); "Online" is a valid
venue for the no-reservation flow and implies has_reservation false. Items
stored before this shape may still carry the legacy equipment_requested /
function_rooms / audiovisual_equipment objects; reads tolerate both.
GSI1 on SUBMISSION is written on create/update (org + submission id).
Admin GET /admins/submissions lists organizations, then queries GSI1 for each
one with GSI1SK beginning SUBMISSION#. Event rows on the same partition are
not included. organization_id is that GSI1PK without the prefix.
organization_name is the name on that ORGANIZATION item.
The student org submission list (GET /students/submissions) queries the
same GSI1 SUBMISSION# rows directly, so every paper is returned no matter
how many events the org has; only the deadlines list still walks EVENT
GSI1 (first 25). GSI2 is the signatory inbox. It stays on return (status
"returned") so the same desk and the student both still see the paper.
The student may edit a returned paper; PUT sets status back to "pending"
and keeps current_signatory / GSI2 on that desk. Deny sets status
"denied", drops GSI2, and the student cannot edit. GSI2 is also dropped
on the last approve (status stays "approved" / "denied", current_signatory
is left as the last desk).

"cancelled" is a terminal, post-approval status set ONLY by a CDM cancel
resolution of a RESERVATION_CHANGE (see below) — never by the student edit path
(WriteSubmission treats it like approved/denied/finished and refuses to edit
it). Cancelling releases every linked BOOKING and removes booking_refs in the
same write as the status flip; the paper is kept (never deleted), stays listed
everywhere, and is excluded from the arcus GET /api/v1/arcus/events list. A
reschedule resolution keeps status "approved" and rewrites
activity_details.date_of_event / day_of_event / time_of_event plus
venue_reservation.reservations[] and booking_refs in lockstep with the edited
holds.

COLLABORATION POINTER (index-only, one per dependent organization)
PK: ORGANIZATION#uuid   (the dependent org, not the proponent)
SK: COLLAB#EVENT#uuid#SUBMISSION#uuid
event_id: EVENT#uuid
submission_id: SUBMISSION#uuid
sent_at: timestamp
The master SUBMISSION item stays the single source of truth. This pointer only
makes the proponent's submission discoverable in a dependent's dashboard: the
student org list queries the base table on PK = ORGANIZATION#<dep> with SK
beginning COLLAB# (no GSI is needed — DynamoDB cannot index the N values of an
array), then resolves each pointer against the master SUBMISSION. The pointer
carries NO form content. WriteSubmission maintains them: create puts one per
dependent, update diffs the dependent set against the stored collaboration
(adds new, deletes removed). A dependent reads the shared submission and its
NOTIFICATION timeline through SubmissionAccess (requireProponent false) but
cannot edit or resubmit — only the proponent (the event's GSI1PK org) may PUT.
role on the API response is "dependent" for these rows, "proponent" otherwise.

POSTEVAL (post-evaluation filed by the org submitter after the event is held)
PK: EVENT#uuid
SK: POSTEVAL#uuid
entity_type: "posteval"
organization_id: string   (bare ORGANIZATION uuid)
event_id: string          (bare EVENT uuid)
submission_id: string     (bare SUBMISSION uuid — the linked approved paper)
status: "submitted" | "approved" | "denied"
submitted_at: timestamp
approved_at: timestamp   (sparse: stamped on OSAAR approve)
denied_at: timestamp     (sparse: stamped on OSAAR deny)
event_title: string      (snapshot of activity_details.title_and_nature)
section_summary: string  (100-500 chars; how the event went, issues, etc.)
financial_report: {
  budget_items: [{ item, unit, quantity, budgeted_total, actual_amount }]
  added_items:  [{ item, unit, quantity, price_per_unit, actual_amount }]
  initial_grand_total: number
  actual_grand_total: number
}
participation_snapshot: {
  attendance_count: number
  attendance:  [{ student_id, full_name, department, member_organization, scanned_at, left_at }]
  evaluation_count: number
  evaluations: [{ evaluation_id, student_id, full_name, participated, filed_at }]
}
GSI1PK: ORGANIZATION#uuid
GSI1SK: POSTEVAL#uuid   (org discovery, mirrors SUBMISSION)

One active POSTEVAL per event; denied filings remain as history when re-filed.
Filed by the org submitter while the event's 3-day
evaluation window is open. WritePostEval gates the write: the linked SUBMISSION
must be approved/finished (422 otherwise), EventWindow::EVALUATION must still be
open (422 "The post-evaluation window is closed for this event."), and no
submitted/approved POSTEVAL may already exist for the event (409). Amounts are
capped at 5 digits (0-99999) and the summary at 100-500 chars. It freezes
participation_snapshot by aggregating the event's MEMBER#/EVALUATION# children
(see below) at write time. The item is put with an attribute_not_exists(PK)
guard on the SK.
ListOrgPostEvals reads GSI1PK=ORGANIZATION#id with GSI1SK begins POSTEVAL#
(student dashboard); ScanPostEvals walks every org's GSI1 the same way for the
OSAAR cross-org queue (optional status filter). GetPostEval fetches one by
PK/SK; single-record detail responses re-aggregate the live participation
snapshot on top of the stored one.
ApprovePostEval sets status=approved + approved_at, then transitions the linked
SUBMISSION approved -> finished (+ finished_at) — both idempotent, and the
window is NOT re-checked (approval may follow the window closing). DenyPostEval
sets status=denied + denied_at and leaves the submission approved. Approving a
denied post-eval, or denying an approved one, aborts 422.

EVENT-partition children written by the arcus companion apps (SAME physical
table, keyed by the apex event_id — apex never writes these, it only reads them
via AggregateEventParticipants to build a POSTEVAL participation_snapshot and
serve the live officer panel). Attendance is captured on the event day;
participant evaluations use the evaluation window and require a check-in.

ATTENDANCE CHECK-IN (arcus-attendance scanner)
PK: EVENT#uuid
SK: MEMBER#{studentId}
member_organization: string
scannedAt: timestamp
leftAt: timestamp   (sparse)
The student's profile is a separate arcus-owned item PK = SK = STUDENT#{studentId}
holding student_id, full_name, course, department (renamed from the former
MEMBER# profile). The EVENT check-in SK above stays MEMBER#{studentId} because
apex splits an EVENT partition's children by SK prefix (MEMBER# = attendance,
EVALUATION# = evaluation); AggregateEventParticipants resolves each check-in's
name by reading the STUDENT#{studentId} profile.

DEPRECATED: arcus-attendance registration used to write its own ORGANIZATION +
MEMBER join rows (PK = ORGANIZATION#uuid, SK = MEMBER#{studentId}, carrying
organization_id + student_id but NO lastname/firstname) to track membership.
Membership is now apex-owned (see ORGANIZATION MEMBER above), so registration no
longer writes them and scripts/migrate_member_to_student.py deletes the
leftovers.

PARTICIPANT EVALUATION (arcus-evaluation authenticated student form)
PK: EVENT#uuid
SK: EVALUATION#{evaluationId}
evaluationId: string
studentId: string
fullName: string
participated: "yes" | "no"
filedAt: timestamp
eventId: string   (the apex event id, for attribution)
This slim EVENT-partition copy supports begins_with(SK,'EVALUATION#'). Apex reads
camelCase attributes (with snake_case fallbacks) and converts participated to a
boolean explicitly ("no" is false).

FULL EVALUATION RESPONSE (arcus-owned; schemaVersion 2)
Detail: PK = SK = EVALUATION#{evaluationId}
List: PK = EVALUATION, SK = {filedAt}#{evaluationId}
Both store evaluationId, studentId, fullName, programYear, organizationName,
department, recentActivity, dateParticipated, participated, filedAt, eventId,
eventTitle, schemaVersion: 2, ratings: map of criterion ID -> number (1-5),
discoverySources: map of source -> boolean, comments: string, othersSpecify: string.
All 23 ratings are required for participated=yes; the nonparticipating form can
omit ratings. Detail, list, and slim event child are written atomically through
TransactWriteItems with attribute_not_exists(PK) on each Put.
New records have no S3 bucket/key; the unchanged FM-SA-05-01 template is filled
in the browser for preview/download and officer export. Legacy metadata remains
visible but cannot regenerate PDFs without the original responses; old S3
objects are not migrated or deleted.
Officer export queries only the authorized EVENT partition, then BatchGetItem
reads EVALUATION detail records in chunks of 100 with bounded retries. Responses
are sorted newest-first and the UI returns at most 100 filtered records.
Student identity is session-derived from Cognito custom:student_id; the server
resolves the profile and rechecks in-window attendance before accepting a filing.

NOTIFICATION
PK: SUBMISSION#uuid
SK: NOTIFICATION#timestamp
signatory: SIGNATORY#uuid
notif_type: "approved" | "fully approved" | "denied" | "returned" | "event scheduled" | "reservation change requested" | "reservation cancelled" | "reservation rescheduled" | "reservation change denied"
comment: string (mandatory if denied or returned)

Students GET / POST / PUT the timeline for their org's paper.
Signatories POST a row on an open desk (does not change submission status)
and PUT a row they authored. POST writes SK = now (UTC, second precision).
PUT replaces notif_type / comment in place; SK does not change.
Students may also change signatory on PUT. Signatory PUT keeps the author.
Approve / return / deny still insert a NOTIFICATION row as a side effect.

The four "reservation ..." notif_type values are system-only (written server-side
by RequestReservationChange / ResolveReservationChange, never client-postable via
StoreNotificationRequest): "reservation change requested" carries an empty
signatory (student-initiated, timeline row only); the other three carry the
resolving CDM signatory and each also triggers an SES email to the student.

SIGNATORY
PK: SIGNATORY#uuid
SK: SIGNATORY#uuid
name: string
role: "adviser" | "cdm" | "dean" | "osaar" | "admin"
department: string (deans only, e.g. SOIT)
GSI4PK: ROLE#ADVISER | ROLE#CDM | ROLE#DEAN | ROLE#DEAN#{DEPARTMENT} | ROLE#OSAAR | ROLE#ADMIN
GSI4SK: SIGNATORY#uuid

A SIGNATORY item is the person. It has no organization_id.
GET /signatories/me and admin list/show read this item.
Who occupies a desk for an org is ORGANIZATION.signatories.
GSI4 is the role index, not an org assignment. ROLE#{ROLE} for adviser, cdm, osaar, admin.
Deans may add a department suffix: ROLE#DEAN#SOIT.

Other items copy the signatory id; they do not join back to SIGNATORY:
  ORGANIZATION.signatories[].signatory_id
  SUBMISSION.current_signatory and GSI2PK (inbox)
  NOTIFICATION.signatory (timeline snapshot)
DELETE /admins/signatories/{id} is guarded: it removes the item only when the
person occupies no ORGANIZATION.signatories desk and has no in-flight GSI2
inbox item; otherwise it returns 409 (leaving the item untouched). Delete does
not rewrite the copies above, so prefer replacing a person in place by keeping
the same uuid (PUT name / role / department). A new uuid leaves in-flight
papers, org desks, and Cognito custom:signatory_id pointing at the old id.

ANNOUNCEMENT
PK: ANNOUNCEMENT
SK: timestamp
content: string

All announcements share one partition. List is Query PK = ANNOUNCEMENT
(newest SK first). Show / PUT / DELETE use GetItem / PutItem / DeleteItem
on that PK + SK. SK is the identity (`sent_at` in the API). POST writes
SK = now (UTC, second precision). PUT replaces content in place; it does
not change SK. Admin Cognito group only.

CAMPUS
PK: CAMPUS#uuid
SK: CAMPUS#uuid   (same as PK)
name: string
classroom_name_prefixes: [string]   (L of S; optional classroom naming rule)
classroom_name_digits: number        (N; optional; pairs with the prefix list)

A reservable campus (e.g. "Intramuros Campus", "Makati Campus"), seeded by
osaar on the /campus page. The SAAF reservation step and the
activity_details.venue dropdown read the list (GET /students/campuses). List
scans PK begins_with CAMPUS# AND PK = SK. DELETE /admins/campuses/{id} is
guarded: 409 if any RESERVABLE still lives under PK = CAMPUS#id (delete those
first); otherwise it removes the item. Rename in place (PUT) to keep the same
uuid so RESERVABLE children and stored booking campus_id snapshots stay valid.

classroom_name_prefixes/classroom_name_digits are the campus's optional
classroom naming rule (e.g. Makati prefixes [MPO, N, W, S, E, NW, SW, SE, NE] +
3 digits -> MPO123, NW045). They are stored together ONLY when both are
supplied; a campus without a rule keeps neither attribute. Prefix tokens are
normalized uppercase and deduped (1-10 letters, up to 30); digits is 1-4. CDM
can flag a RESERVABLE room as a classroom only when its owning campus defines a
rule, and the room name must be <one prefix><exactly N digits> (case-
insensitive). Rule lives in App\Aws\DynamoDb\CampusClassroomNaming (backend) and
lib/campus-classroom-format.ts (frontend) so form and API never drift.

RESERVABLE (a bookable room or equipment item under a campus)
PK: CAMPUS#uuid
SK: RESERVABLE#uuid   (globally unique; doubles as the BOOKING partition key)
name: string
type: "room" | "equipment"
schedule: {
  monday:    [bool x12]
  tuesday:   [bool x12]
  wednesday: [bool x12]
  thursday: [bool x12]
  friday:    [bool x12]
  saturday:  [bool x12]
}
min_participants: number   (room-only; N attribute, optional = no lower limit)
max_participants: number   (room-only; N attribute, optional = no upper limit)
is_classroom: bool         (room-only; true when the name must match the campus classroom format)
max_quantity: number       (equipment-only; N attribute, optional = absent means unlimited)

The recurring weekly availability template. Days run monday..saturday (Sunday
is never reservable and is not stored); each present day is exactly 12
booleans, one per 70-minute slot of the 07:00-21:00 window (true = available),
and an absent day is all-unavailable. Added/edited by cdm on the /reservables
page (CSV for name+type, a grid for the schedule). listByCampus queries
PK = CAMPUS#id, SK begins_with RESERVABLE#. DELETE
/admins/campuses/{campus}/reservables/{id} is guarded: 409 if any BOOKING still
occupies PK = RESERVABLE#id (release those first). Canonical slot math lives in
App\Aws\DynamoDb\ReservableSchedule (backend) and lib/schedule-slots.ts
(frontend) so indices/times never drift.

min_participants/max_participants bound the headcount a room can hold. They are
persisted ONLY when type is "room" and at least one bound is supplied (the API
silently drops them for equipment, and a room with neither attribute is treated
as unlimited). On a SAAF submit the activity's expected_participants is checked
against each picked room's bounds in BookingRecords::assertAvailable; an
out-of-range headcount aborts with 422 before any BOOKING is written. The human
"capacity_label" in the API response is derived, not stored.

is_classroom marks a room as a classroom. It is persisted ONLY when type is
"room" and the flag is true (equipment and non-classroom rooms omit it, read
back as false). When set, create/update enforces that the owning campus defines
a classroom naming rule and that this room's name matches
<one prefix><exactly N digits> from that rule (422 otherwise) -- see the CAMPUS
classroom_name_prefixes/classroom_name_digits note above. Enforced at reservable
create/update only; the SAAF reservation step and CSV import do not set it.

max_quantity caps how many units of an equipment item may be booked across all
approved holds on a given date (e.g. a campus has 10 laptops: max_quantity=10).
It is persisted ONLY when type is "equipment" -- sending it for a room returns
422 (StoreReservableRequest after() cross-field check). When absent (or null),
the item is treated as unlimited. The availability endpoint derives
booked_quantity (sum of quantity_requested across all approved BOOKINGs for that
date) and remaining_quantity (max_quantity - booked_quantity, floor 0) from
BookingRecords::bookedQuantitiesByDate; these are returned in the per-date
availability map alongside booked_slots/available_slots.

BOOKING (a concrete hold on a reservable's slots for specific dates)
PK: RESERVABLE#uuid
SK: BOOKING#uuid
timestamp: string   (create time, UTC "Y-m-d\TH:i:s\Z")
schedule_selected: [{ date: "YYYY-MM-DD", slots: [int 0-11] }]   (normalized: unique sorted slots, dates sorted)
source: "submission" | "cdm"
campus_id: string                       (as sent; bare uuid)
reservable_name: string                 (snapshot at write time)
reservable_type: "room" | "equipment"   (snapshot at write time)

One BOOKING per (reservable, submission) or per (reservable, CDM reserve
action); schedule_selected lists every selected date+slots for that reservable.
Two flavors share the item type, distinguished by source:

Submission-sourced (source "submission") — written by the SAAF create/update
path (BookingRecords::planForSubmission then commit). Adds GSI5 + traceability
so the owning org can list its holds and CDM can label them read-only:
  GSI5PK: ORGANIZATION#uuid
  GSI5SK: timestamp
  event_id: string          (bare EVENT uuid)
  submission_id: string     (bare SUBMISSION uuid)
  organization_id: string   (bare ORGANIZATION uuid)
  approval_status: "pending" | "approved"
                            (written "pending" by the SAAF path; absent on
                            legacy items, which read as approved)
  approved_at: string       (sparse; stamped when CDM approves the paper)
  approved_by: SIGNATORY#uuid  (sparse; the approving CDM signatory)
  quantity_requested: number   (equipment-only; N attribute; how many units of
                               the item the student requested -- absent on room
                               bookings and legacy equipment bookings, where 1
                               is assumed when computing booked_quantity)
Only approved holds occupy slots. ApproveSubmission flips every booking_refs
hold to "approved" on the paper's last (CDM) approval, after re-checking them
against the approved bookings (409, nothing written, on conflict). A hold
recreated by a RESERVATION_CHANGE room swap is written "approved" directly.
Legacy holds are stamped by scripts/backfill_booking_approval.py.
Released (deleted) when the paper is denied or returned, or reconciled on a
student re-edit — all driven by the SUBMISSION's booking_refs. The CDM
manual-delete route refuses source "submission" with 409 so a live paper's hold
is never deleted out from under it.

Edited in place through a RESERVATION_CHANGE resolution: a same-reservable
date/slot change patches schedule_selected on the existing PK/SK (keys, GSI5
linkage and submission_id/event_id/organization_id all survive, and the
SUBMISSION's booking_refs entry stays valid as-is); a room swap deletes the old
BOOKING and recreates a source:"submission" hold (with GSI5) under the new
RESERVABLE partition, swapping the booking_refs entry to the new keys in the
same submission update. A cancel resolution releases (deletes) every linked hold
and drops booking_refs. See RESERVATION_CHANGE.

Manual (source "cdm") — created by CDM on the /reservables Reserve section
(BookingRecords::createManual). Carries NO GSI5 and NO submission linkage, so it
never surfaces in an org's booking list; it only blocks slots. Adds:
  booked_by: SIGNATORY#uuid   (the CDM signatory, from the JWT)
  reason: string              (optional purpose note; omitted when blank)
Released only by CDM: DELETE
/admins/campuses/{campus}/reservables/{reservable}/bookings/{booking}.

Both flavors share one availability engine (BookingRecords): a slot is free only
when the weekly template allows it AND no approved BOOKING (either source; a
manual hold always counts) occupies that concrete date+slot. Pending holds are
still listed on the CDM calendar and still block reservable deletion. Conflict detection queries the base RESERVABLE partition
(PK = RESERVABLE#id, SK begins_with BOOKING#) — never GSI5 — so it works before
the organization index exists. GSI5 is provisioned in AWS by the operator; the
code writes GSI5PK/GSI5SK on submission-sourced bookings but does not depend on
the index for correctness. There is no automatic expiry on a manual hold.

RESERVATION_CHANGE (a student's request to cancel or reschedule an approved paper's holds)
PK: EVENT#uuid
SK: RESERVATION_CHANGE#uuid
item_type: "reservation_change"
organization_id: string        (bare uuid, snapshot)
submission_id: string          (bare uuid, snapshot)
campus_id: string              (bare uuid, snapshot)
requested_by: string           (STUDENT#<sub> from the JWT)
requested_at: timestamp
request_type: "cancel" | "reschedule"
reason: string                 (required, <=500)
suggested_date: "YYYY-MM-DD"   (sparse: reschedule only; advisory, CDM is not bound by it)
bookings: [{                   (the targeted holds, FROZEN from the paper's live booking_refs at request time)
  pk: "RESERVABLE#uuid", sk: "BOOKING#uuid",
  reservable_id, reservable_name, reservable_type,
  schedule_selected: [{ date, slots }]
}]
status: "pending" | "resolved" | "denied"
GSI6PK: CAMPUS#uuid
GSI6SK: status#requested_at    (pending#..., resolved#..., denied#...)

On resolution (status -> resolved/denied) the item also carries:
decision: "cancel" | "reschedule" | "deny"
resolved_by: SIGNATORY#uuid
resolved_at: timestamp
comment: string
applied: {                     (before/after audit trail; audit only, never read back as source of truth)
  bookings: [{
    pk, sk,                    (original keys)
    action: "released" | "kept" | "updated" | "replaced",
    before: { reservable_id, schedule_selected },
    after:  { reservable_id, schedule_selected } | null,
    new_pk, new_sk             (room swaps only — point at the recreated BOOKING)
  }],
  submission: {
    status_before, status_after,
    date_of_event_before/after, time_of_event_before/after,   (reschedule only)
    booking_refs_before, booking_refs_after
  } | null                     (null for a deny)
}

One pending request per paper. The student side lists the full history with a
base-table query on PK = EVENT#uuid, SK begins_with RESERVATION_CHANGE# (no GSI
needed). The CDM per-campus queue reads GSI6 (GSI6PK = CAMPUS#uuid), optionally
filtered by status. GSI6 is provisioned in AWS by the operator, mirroring how
GSI5 backs the organization booking index; the code writes GSI6PK/GSI6SK but the
CDM list endpoint fails loudly until the index exists. Resolve is guarded: the
request must still be pending (finalize uses a conditional put on
attribute_not_exists(resolved_at) so two CDM users cannot resolve it twice), the
paper must still be approved, and every snapshotted hold must still appear in the
paper's live booking_refs (a stale request aborts 409 with zero writes). The
request window closes at the end of activity_details.date_of_event in
Asia/Manila; CDM may resolve at any time, even after the event day.

Routing is snapshotted onto SUBMISSION at write time. On create (and on a
student PUT that re-routes), the resolver builds an ordered signatory_sequence
of SIGNATORY#uuid ids and stores it on the item. The sequence starts at
Adviser, then Dean when activity_type is co-curricular, then OSAAR, then CDM
when has_reservation is true. If the submitting organization's
is_higher_council is true, Dean is skipped (even for co-curricular);
Adviser still reviews first, then OSAAR, then CDM when there is a
reservation. Adviser and Dean come from ORGANIZATION.signatories. OSAAR and
CDM come from OSAAR_SIGNATORY_ID and CDM_SIGNATORY_ID. admin is a valid desk
role but is not in this sequence. current_signatory / GSI2PK hold whoever has
the paper now; on a fresh submit current_signatory is signatory_sequence[0].
On approve, ApproveSubmission reads the stored signatory_sequence, finds the
current desk, and advances current_signatory / GSI2 to the next id (or drops
GSI2 when the sequence is done) — it no longer re-reads the org desks or
campus env ids. Items written before this field existed have no
signatory_sequence; the first approve lazily resolves it (via the org desks
and campus env ids) and persists it on the same write.
Return keeps the paper on the current desk (status "returned"). A student PUT
on a returned paper keeps that desk only if it is still in the recomputed
sequence; otherwise routing restarts at signatory_sequence[0]. Deny
removes it from the queue (status "denied") and cannot be edited.

When a submission has collaboration dependents, the adviser/dean stage expands
across every organization. The chain is built over [proponent, ...dependents]
in submitted order: first the Adviser of each organization, then the Dean of
each organization (a Dean step for an org exists only when
activity_classification.activity_type is co-curricular AND that org's
is_higher_council is not true), then the campus desks (OSAAR, then CDM when
venue_reservation.has_reservation is true). Signatory ids are de-duplicated
across the whole chain preserving first occurrence, so a person who is adviser
and dean (same or across orgs) signs once. Missing adviser / required dean /
unconfigured campus desk throws UnresolvableSignatoryRoute (422). The rest of
the walk (ApproveSubmission, GSI2 inbox, deny/return) is unchanged — a longer
stored sequence simply means more desks. On a returned re-edit only the
proponent edits and resubmits; the sequence is recomputed, and if the desk the
paper was returned to is no longer in the new chain, routing restarts at
signatory_sequence[0].

signatory_sequence stores bare SIGNATORY#uuid ids in order, which is enough to
route approvals but not to label each hop for a collaboration (two orgs can both
contribute an "adviser"). Detail reads therefore project the stored sequence
into a derived signatory_chain: an ordered array of
{ signatory_id, role, organization_id, organization_name }. SignatoryChainResolver
walks [proponent, ...dependents] org desks to map each id to the role and
organization whose desk it is (first desk wins on a de-duplicated shared
signatory); the campus desks (OSAAR, CDM, matched against the env ids) resolve
to a null organization. signatory_chain is computed on read for the single-record
GET endpoints (student / signatory / admin detail) and is NOT written to the item
and NOT returned by list endpoints — the persisted source of truth stays
signatory_sequence plus the ORGANIZATION.signatories desks.

Deprecated / removed objects

DEADLINE REMINDER (removed)
Was: PK = EVENT#uuid, SK = DEADLINE#uuid, sent_at, deadline.
Reason: orphaned read path with no producer. DynamoKeys::deadline() is defined
but never called, and no route, controller, or writer ever creates a DEADLINE
item. The only read is GET /students/deadlines (ListOrgDeadlines), which walks
each event partition for SK begins_with DEADLINE#. DEADLINE items exist solely
in test fixtures (DeadlineControllerTest) and screenshot mocks
(capture-screenshots.mjs), and delete_events.py only removes them. The object
is therefore deprecated and no longer part of the modeled schema; the dangling
read endpoint still exists in code but returns nothing in production.

SESSION LOG (implemented — session monitoring)
Table: MAPUA_APEX_TABLE (single-table, no separate log table)
Written by: App\Logging\SessionLogWriter
Read by:    App\Logging\LogTableItems::querySessions(), getSessionItem()

Key structure (plan §2.1):
  PK:     SESSION#{session_id}
  SK:     METADATA
  GSI1PK: LOG#SESSION#{YYYY-MM}   GSI1SK: {login_time}   ← monthly query bucket
  GSI2PK: USER#{sub}              GSI2SK: {login_time}   ← per-user session history
  GSI3PK: STATUS#active|completed|timed_out|revoked   GSI3SK: {last_heartbeat}   ← sweep index

Active Session Pointer (Single Source of Truth per user):
  PK: USER#{sub}
  SK: ACTIVE_SESSION
  Fields:
    sub:            string (Cognito user sub)
    session_id:     string (active session_id)
    device_id:      string (client device UUID passed in /sessions/start)
    status:         "active"
    login_time:     ISO-8601 UTC timestamp
    last_heartbeat: ISO-8601 UTC timestamp
    TTL:            unix epoch

Displacement via TransactWriteItems:
When Device B logs in while Device A is active:
1. Update USER#{sub} / ACTIVE_SESSION to session_id=B, device_id=B (condition: session_id = A).
2. Put SESSION#{B} with status = active (condition: attribute_not_exists(PK)).
3. Update SESSION#{A} with status = completed, end_reason = concurrent_login, logout_time = now (condition: status = active).
All three writes occur in a single atomic TransactWriteItems request so Device A is immediately marked completed with zero delay.

Session ID derivation: sha256(sub + ":" + auth_time)
Chain suffix (#2, #3…) appended when base session has ended, giving each
re-authentication a fresh slot without reopening the closed one.

Item fields:
  session_id:              string (UUID-like sha256 hash, possibly with #N suffix)
  sub:                     string (Cognito user sub)
  device_id:               string | null (client device UUID)
  user_name:               string
  user_email:              string
  user_role:               string
  ip_address:              string
  user_agent:              string
  device_info:             map { browser: string, os: string, device_type: string }
  status:                  "active" | "completed" | "timed_out" | "revoked"
  login_time:              ISO-8601 UTC timestamp
  logout_time:             ISO-8601 UTC timestamp | null
  last_heartbeat:          ISO-8601 UTC timestamp
  duration_seconds:        number (updated on heartbeat and close)
  pages_visited:           list<{ path: string, timestamp: string }> (max 200 entries)
  pages_visited_truncated: boolean
  events_count:            number
  revocation_reason:       string | null
  TTL:                     unix epoch (config aws.dynamodb.log_retention_days, default 90 days)

Stale threshold: 15 minutes (no heartbeat → timed_out)
Sweep command:   sessions:sweep-stale (artisan, scheduled every 10 minutes via console.php)
